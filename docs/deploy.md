# Rolling update на одной ВМ в Yandex Cloud

Приложение работает в Docker Swarm на существующей ВМ `fellow-travelers`.
GitHub Actions собирает образы в Yandex Container Registry, передаёт секреты по SSH
и запускает контроллер [`deploy/swarm.py`](../deploy/swarm.py).

Два независимых стека используют общую attachable overlay-сеть `fellow-private`:

| Стек | Сервисы | Как обновляется |
| --- | --- | --- |
| `fellow` | `api` × 2, `web` × 2, `bot` × 1, `worker` × 1 | Каждый релиз приложения |
| `fellow-infra` | PostgreSQL, Caddy, ежедневные бэкапы | Первый переход и явный `update_infra` |

Caddy принимает 80/TCP и 443/TCP+UDP, направляет запросы на `web`; nginx передаёт
`/api/` в `api`. Служебные `/readyz`, `/healthz`, `/metrics` остаются внутри сети.
Порты PostgreSQL, API и worker наружу не публикуются. Swarm рекламирует приватный
адрес ВМ; его служебные порты не нужно открывать в публичной группе безопасности.

## Обычный релиз

Push в `main` запускает [Deploy](../.github/workflows/deploy.yml) после успешного CI.
Также доступен Actions → Deploy → Run workflow → `action=deploy`.

1. Actions собирает API и web с тегом коммита. BuildKit повторно использует кеш.
2. Устанавливает новую версию секретных файлов на ВМ.
3. Контроллер получает образы, фиксирует их digest и проверяет запуск приложения
   с секретными файлами до изменения работающих сервисов. `latest` не используется.
4. Копирует файлы `assets` новой сборки в общий том `fellow-assets`, сохраняя старые.
5. Один раз выполняет `alembic upgrade head` и загрузку справочника аэропортов.
6. Swarm обновляет API и web по одной реплике с `order: start-first`: запускает
   новую до остановки старой. API проверяет `/readyz`, включая подключение к БД.
7. Бот и worker обновляются с `stop-first`, по одному экземпляру. Это исключает
   два одновременных long-polling клиента Telegram и смешение версий обработчика задач.
8. Контроллер ждёт завершения обновления, проверяет готовность всех контейнеров
   и их стабильную работу. Проверяет API напрямую, сайт, `/api/v1/me` через nginx
   (ожидается 401 без авторизации) и публичный HTTPS-сайт.
9. Только после успешных проверок сохраняет новый `current.json`.

При неудаче Swarm откатывает проблемный сервис, а контроллер возвращает **весь стек
приложения** к предыдущему успешному описанию и проверяет его. Workflow завершается
ошибкой даже при успешном восстановлении. Схема БД автоматически не откатывается.

PostgreSQL, Caddy и backup при обычном релизе не пересоздаются. Пути их секретов
закреплены за первым инфраструктурным релизом. API получает до 45 секунд на завершение
запросов, Docker ждёт до 60 секунд; у worker также есть 60 секунд на текущую задачу.
Бот при обновлении на короткое время перестаёт принимать новые сообщения.

Старые JS/CSS остаются доступны всем репликам web. Уже открытая страница может
загрузить свой старый chunk и после обновления. Том `fellow-assets` нельзя очищать
при деплое; чистка требует отдельной политики хранения.

## Секреты и права

В GitHub Settings → Secrets and variables → Actions должны быть заданы:

| Секрет | Назначение |
| --- | --- |
| `YC_SA_KEY` | JSON-ключ сервисного аккаунта CI для выпуска IAM-токена |
| `YC_REGISTRY_ID` | ID Container Registry |
| `YC_VM_ID` | ID существующей ВМ |
| `YC_VM_SSH_KEY` | Отдельный приватный ключ Actions без passphrase |
| `YC_VM_SSH_KNOWN_HOSTS` | Проверенная запись SSH host key для IP ВМ |
| `BOT_TOKEN` | Токен продакшен-бота |
| `BOT_USERNAME` | Username без `@`; встраивается также во фронтенд |
| `POSTGRES_PASSWORD` | Текущий пароль роли `fellow`, только буквы и цифры |
| `SITE_ADDRESS` | Домен, сейчас `fellowtravelers.ddns.net`; для HTTP допустимо `:80` |
| `ACME_EMAIL` | Email аккаунта ACME |
| `TELEGRAM_RELAY_URL`, `TELEGRAM_RELAY_SECRET` | Необязательная пара настроек Telegram relay |

Необязательные настройки: `INIT_DATA_MAX_AGE_SECONDS` (86400), `DEBUG` (false),
`ACME_CA` (боевой Let's Encrypt). Actions Variable `YC_VM_SSH_USER` по умолчанию
равна `yc-user`.

Публичная часть SSH-ключа должна быть в `~yc-user/.ssh/authorized_keys`.
Пользователю требуется `sudo -n python3`: контроллер управляет Docker и первым
переходом с COI. Host key проверяется с `StrictHostKeyChecking=yes`; не заменять
это доверием к `ssh-keyscan` во время релиза.

CI нужны права на push образов и чтение адреса ВМ. Управление метаданными Compute
больше не используется. Сервисному аккаунту ВМ нужны права pull образов.
Контроллер передаёт авторизацию Swarm через `--with-registry-auth`, чтобы контейнеры
могли получать приватные образы. Локальный Docker config контроллера временный.

Секреты передаются только в stdin SSH и лежат в закрытых каталогах:

```text
/var/lib/fellow-travelers/secrets/<run_id>-<attempt>/
  api/{database_url,bot_token}
  bot/{database_url,bot_token,telegram_relay_secret}
  db/password
  backup/pgpass
```

Они подключаются read-only через `/run/secrets`. Значений нет в спецификациях,
метаданных COI или `docker inspect` Env новых контейнеров. Администратор Docker
имеет доступ к файлам и секретам. Старые каталоги нельзя удалять, пока они нужны
работающим сервисам или откату. Пароль уже созданной роли PostgreSQL не меняется
через `POSTGRES_PASSWORD_FILE`; контроллер отклоняет его случайную смену.
Ротация требует отдельной процедуры изменения роли и инфраструктурных файлов.

## Первый переход с COI

Bootstrap рассчитан на существующий работающий стек COI с контейнерами `api`,
`web`, `bot`, `worker`, `db`, `caddy`, `backup`. На пустой ВМ этот контроллер
не создаёт приложение с нуля.

Первый запуск контроллера без `current.json`:

- находит реальные имена томов работающих контейнеров и фиксирует их как external;
- сохраняет root-only снимок конфигурации контейнеров и дамп БД в custom-формате;
- создаёт Swarm и сеть, заранее получает образы и сохраняет assets;
- отключает `yc-container-daemon.service`, останавливает старые контейнеры;
- запускает инфраструктуру с теми же томами, затем приложение;
- при ошибке удаляет новые стеки, дожидается остановки их контейнеров и возвращает COI.

Первый переход требует короткого перерыва. Для последующих релизов API/web
используется rolling update. Старые контейнеры остаются остановленными для
аварийного восстановления; они могут содержать прежние секреты в Env.

Не запускайте старый workflow, `yc compute instance update-container` или COI-агент
после перехода: Swarm должен оставаться единственным управляющим контейнерами.
Обычная перезагрузка ВМ сохраняет Swarm и external volumes; COI-агент отключён.

## Откат и миграции

Actions → Deploy → Run workflow → `action=rollback`. Контроллер использует описание
предыдущего успешного релиза, включая digest образов и прежние пути секретов.
Повторная сборка и миграции при таком откате не выполняются. Если проверка отката
провалится, контроллер вернёт текущий релиз. Инфраструктура при ручном откате
приложения не меняется.

Для аварийного отката по SSH можно запустить сохранённый контроллер:

```bash
printf '%s' '{"action":"rollback"}' | sudo python3 \
  /var/lib/fellow-travelers/swarm/releases/<release>/swarm.py
```

Изменения схемы обязаны поддерживать обе версии кода, работающие одновременно:
сначала добавить новые таблицы/nullable-поля, обновить код, заполнить данные,
и лишь отдельным последующим релизом удалять старые поля. Автоматический откат
контейнеров не отменяет миграции. Не применять `alembic downgrade` автоматически:
он может удалить данные и сломать ещё работающие реплики.

Блокировка `deploy.lock` на ВМ защищает от двух параллельных контроллеров;
Actions также сериализует релизы через `concurrency`. Не прерывайте работающий
контроллер во время первого перехода.

## Инфраструктура, HTTPS и обслуживание

Для обновления Caddy или настроек домена/ACME: Run workflow → `action=deploy`,
`update_infra=true`. При этом собирается Caddy и обновляется инфраструктурный стек;
возможен короткий перерыв HTTPS. PostgreSQL сохраняет прежний путь секретов и том.
Обычный релиз отклоняет изменение домена/ACME без `update_infra`.

A-запись домена должна указывать на публичный IP ВМ, 80/TCP и 443/TCP+UDP должны
быть открыты. Caddy получает и продлевает сертификаты автоматически; тома `/data`
и `/config` сохраняются с COI. Не удаляйте их и не закрывайте порт 80.

```bash
sudo docker stack services fellow
sudo docker stack services fellow-infra
sudo docker service ps fellow_api --no-trunc
sudo docker service logs --tail 100 -f fellow_api
sudo docker service logs --tail 100 -f fellow_bot
sudo docker service logs --tail 100 -f fellow_worker
sudo systemctl is-enabled yc-container-daemon.service  # ожидается disabled
```

Состояние релизов: `/var/lib/fellow-travelers/swarm/current.json` и
`releases/<release>/{app.yml,infra.yml,manifest.json,swarm.py}`. При ошибке команды
закрытые диагностические данные остаются в `swarm/last-error.log`: не публикуйте
их без проверки на секреты. Первичный снимок `legacy-containers.json` и дамп
`before-cutover.dump` также содержат конфиденциальные данные и доступны только root.

Backup раз в сутки сохраняет `day1.sql.gz`…`day7.sql.gz` в прежнем томе `coi_backups`.
Повреждённый дамп не заменяет предыдущую успешную копию. Бэкапы на том же диске
не защищают от его потери; для этого нужна отдельная выгрузка в Object Storage.

Для получения ID контейнера БД и дампа:

```bash
DB_CONTAINER=$(sudo docker ps -q --filter label=com.docker.swarm.service.name=fellow-infra_db)
sudo docker exec "$DB_CONTAINER" pg_dump -U fellow -d fellow_travelers -Fc > backup.dump
```

Для Registry сохраняется политика [`deploy/lifecycle-rules.json`](../deploy/lifecycle-rules.json).
Перед очисткой образов учитывайте digest текущего и предыдущего успешного релиза.

## Проверки и ограничения

CI проверяет конфигурацию, передачу секретов, порядок миграций и развёртывания,
откат всего приложения, отказ первого перехода и защиту от двух PostgreSQL на одном
томе. Интеграционная проверка в изолированном Swarm покрывает медленный старт
новой реплики и автоматический откат при неуспешном healthcheck.

На ВМ требуется запас памяти для третьей временной реплики API/web. Текущая ВМ:
2 CPU, 4 ГБ RAM. Локальные тома привязывают эту конфигурацию к **одному узлу**;
контроллер отклоняет многоузловой Swarm. Rolling update снижает перерыв при
деплое приложения; отказ самой ВМ или PostgreSQL остановит сервис.
