# Контракты фронтенд ↔ бэкенд

Источник истины — [`openapi.yaml`](openapi.yaml) (OpenAPI 3.1). Здесь — общие соглашения, которые в схеме
выражены плохо. Изменения контракта согласуем с фронтом **до** реализации.

Пометки в схеме: `x-stage: pre-mvp` — нужно для pre-MVP, `x-stage: mvp` — появится в MVP
(можно не реализовывать на первом этапе, но форма данных уже зафиксирована).

## 1. Базовое

- База: `https://<host>/api/v1`. Формат — JSON, UTF-8. Поля — `snake_case`.
- Идентификаторы — UUID-строки.
- Отсутствующее значение — `null` (поле присутствует), а не пропуск поля.
- Списки без пагинации на pre-MVP (группа — десятки/сотни участников). Если понадобится — добавим `?cursor=`.

## 2. Аутентификация

Мини-приложение передаёт `Telegram.WebApp.initData` **как есть** в каждом запросе:

```
Authorization: tma <initData>
```

Бэкенд проверяет подпись (HMAC-SHA256 от токена бота) и `auth_date` (не старше 24 ч). Пользователь создаётся
автоматически при первом запросе. Ошибка подписи → `401 UNAUTHORIZED`.

**Телефон.** Мини-приложение телефон не передаёт: пользователь отправляет контакт боту, бот сохраняет его на
бэкенде. Фронт смотрит `GET /me` → `phone`/`has_phone`. Без телефона:
- можно смотреть приглашение и вступать в группу;
- нельзя отправить заявку → `403 PHONE_REQUIRED`. Фронт показывает объяснение и кнопку «Поделиться контактом»
  (`Telegram.WebApp.requestContact()` либо возврат в бота); после этого перезапрашивает `GET /me`.

## 3. Ошибки

Любой ответ 4xx/5xx:

```json
{ "error": { "code": "JOIN_CLOSED", "message": "Вступление в группу закрыто", "details": null } }
```

`message` — человекочитаемый текст на русском, его можно показать как есть. Логика фронта завязывается на `code`.
Для `422 VALIDATION_ERROR` в `details.fields` — словарь `поле → текст ошибки`.

| HTTP | code | Когда |
| --- | --- | --- |
| 422 | `VALIDATION_ERROR` | Неверные/недостающие поля |
| 401 | `UNAUTHORIZED` | Нет или невалиден `initData` |
| 403 | `FORBIDDEN` | Нет прав (не админ группы, не член группы) |
| 403 | `PHONE_REQUIRED` | Действие требует телефона |
| 404 | `NOT_FOUND` | Ресурса нет или он недоступен пользователю |
| 404 | `INVITE_NOT_FOUND` | Неверный код приглашения |
| 409 | `JOIN_CLOSED` | Вступление в группу закрыто |
| 409 | `APPLICATION_LOCKED` | Заявку уже нельзя менять (назначен трансфер на pre-MVP / уже уехал) |
| 409 | `ALREADY_DEPARTED` | Действие недоступно после отметки «Уехал» |
| 409 | `CAPACITY_EXCEEDED` | Заявка/состав не влезает в машину (3 пассажира, 2 места багажа) |
| 409 | `TRIP_IN_USE` | Нельзя удалить рейс — на него ссылаются заявки |
| 409 | `INCOMPATIBLE_TRANSFER` | (MVP) Ручной состав нарушает правила ожидания/вместимости |
| 503 | `FLIGHT_PROVIDER_UNAVAILABLE` | (MVP) Поставщик рейсов недоступен |

## 4. Время и даты

- Моменты времени — ISO 8601 **со смещением**: `"2026-11-12T10:05:00+03:00"`. Бэкенд отдаёт смещение
  часового пояса соответствующего аэропорта (вылет — по аэропорту вылета, прилёт — по аэропорту прилёта).
- У каждой точки (`Location`) есть `timezone` (IANA, `"Europe/Moscow"`) — для расчётов на клиенте
  (обратный отсчёт, «+1 сутки»).
- Даты без времени (даты мероприятия) — `"2026-11-12"`.
- При вводе рейса админ передаёт время **с локальным смещением аэропорта** либо без смещения — тогда бэкенд
  интерпретирует его в таймзоне аэропорта.

## 5. Статусы

**Статус заявки** `ApplicationStatus` (то, что видит участник, CAP-07):

| Значение | UI-текст |
| --- | --- |
| `searching` | Ищем попутчиков |
| `assigned` | Группа назначена (есть трансфер) |
| `solo` | Еду самостоятельно |
| `cancelled` | Участие отменено |

**Отметки** — отдельно от статуса: `at_meeting_point: bool` («Я на месте»), `departed_at: datetime|null` («Уехал»).
После `departed_at != null` любые изменения заявки → `409 ALREADY_DEPARTED`.

**Статус рейса** `TripStatus` (MVP, на pre-MVP всегда `scheduled`): `scheduled`, `delayed`, `departed`,
`landed`, `cancelled`, `unknown`. Источник данных `source`: `manual` | `provider`.

Переходы заявки:

```
           PUT (первая отправка)
                 │
                 ▼
   ┌────────► searching ──(подбор)──► assigned
   │             │  ▲                   │
   │   go-solo   │  │ resume-search     │ go-solo / cancel / (MVP) несовместимое изменение
   │             ▼  │                   ▼
   │            solo ◄──────────────────┘ (выход из трансфера)
   │             │
   └─ resume ────┤ cancel
                 ▼
             cancelled  (resume-search возвращает в searching)
```

## 6. Ссылки и deep link

- Приглашение: `invite.link` = `https://t.me/<bot>?startapp=join_<code>` (открывает мини-приложение сразу).
  Код `invite.code` — 6 символов `[A-Z0-9]`, без регистра, вводится вручную.
- `start_param` мини-приложения (`Telegram.WebApp.initDataUnsafe.start_param`):

| start_param | Что открыть |
| --- | --- |
| `join_<CODE>` | Экран приглашения → `GET /invites/{code}` |
| `event_<uuid>` | Моя поездка в группе → `GET /events/{id}/my-trip` |
| `admin_<uuid>` | Управление группой → `GET /events/{id}/admin/participants` |
| отсутствует | Список моих групп → `GET /me/events` |

Те же значения используют кнопки бота и (MVP) уведомления.

## 7. Обновление данных

Push/WebSocket нет. Фронт перезапрашивает данные при открытии экрана и по pull-to-refresh (CAP-07).

## 8. Основные экраны → эндпоинты

| Экран | Запросы |
| --- | --- |
| Старт / профиль | `GET /me` |
| Мои группы | `GET /me/events` |
| Создание / настройка группы | `POST /events`, `PATCH /events/{id}`, `GET /events/{id}/invite` |
| Приглашение | `GET /invites/{code}`, `POST /invites/{code}/join` |
| Рейсы группы (админ) | `GET/POST /events/{id}/trips`, `PATCH/DELETE /trips/{id}`, `GET /locations` |
| Заявка | `GET /events/{id}/trips`, `GET/PUT /events/{id}/my-application` |
| Моя поездка | `GET /events/{id}/my-trip`, действия `POST /events/{id}/my-application/{go-solo,resume-search,cancel}`, `PUT .../marks` |
| Управление: участники | `GET /events/{id}/admin/participants`, `GET /events/{id}/admin/transfers` |
| (MVP) Табло, правка составов | `GET /events/{id}/admin/board`, `PUT /events/{id}/admin/transfers/{tid}/members`, `POST .../admin/applications/{aid}/departed` |

## 9. Роли и доступ

- Создатель группы — её админ (`is_admin=true`). Участником он **не становится автоматически**
  (`is_participant=false`): если едет сам, вступает по своему же приглашению и заполняет заявку.
- Пользователь, который не админ и не участник группы, получает `404 NOT_FOUND` на любые её ресурсы —
  существование группы не раскрываем.
- Участник, который пытается выполнить действие админа, получает `403 FORBIDDEN`.
- `PATCH` различает «поле не передано» и `null`: `null` допустим только для `pickup_point` (сброс —
  посадка там же, где сбор) и `chat_url` (удалить ссылку).
- Во входных телах лишние поля запрещены → `422 VALIDATION_ERROR` («Лишнее поле»).

## 10. Заявка: поведение, важное для UI (pre-MVP)

- Подать заявку может только **участник** группы. Админ без участия получает `403 FORBIDDEN` —
  UI предлагает вступить по своему приглашению.
- Ответ на `PUT /my-application` и на действия уже отражает результат подбора: если попутчики нашлись
  сразу, придёт `status: "assigned"` и `transfer_id`.
- `PUT` при статусе `assigned` → `409 APPLICATION_LOCKED`: чтобы изменить заявку, участник сначала
  выходит из трансфера («Еду самостоятельно» или «Отменить»), затем «Вернуться в поиск».
- `PUT` при статусе `solo` меняет данные, но статус остаётся `solo`; при `cancelled` — заявка
  возвращается в `searching`.
- Если из трансфера вышел один из двоих, трансфер расформировывается, оставшийся снова ищет попутчиков.
  Если из троих — двое остаются вместе (замену в pre-MVP не ищем).
- «Уехал» необратимо в pre-MVP: после него любые изменения → `409 ALREADY_DEPARTED`. Отметка
  «Уехал» не меняет статус заявки.
- Повторные `go-solo`, `resume-search`, `departed=true` идемпотентны — отвечают `200` с текущим состоянием.
