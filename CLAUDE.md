# fellow-travelers — правила для Claude

Сервис поиска попутчиков (Telegram-бот + мини-приложение + бэкенд). Требования — `docs/Capabilities_Poputchiki.md`,
план бэкенда — `docs/backend-plan.md`, контракты фронт ↔ бэк — `docs/contracts/`.

Наша зона — **бэкенд** (`backend/`). Фронтенд (`frontend/`) делает другая команда; связь с ней только через контракты.

## Git

- Работаем в feature-ветках (`feature/...`), коммиты в них делает основная сессия — небольшими логическими шагами.
- **Никогда не коммитить в `main` и не пушить** — merge и push делает пользователь.
- Агенты-исполнители не коммитят: коммит делает оркестратор после ревью.
- `.idea/` и прочие локальные файлы не добавлять.

## Разделение моделей: планирует сильная, исполняет слабая

Основная сессия запускается на самой сильной модели (Opus). Она **не пишет код задач сама**, а работает как
архитектор и оркестратор:

1. **Планирование.** Разбирает задачу, читает требования и контракты, решает архитектурные вопросы,
   разбивает работу на небольшие независимые подзадачи.
2. **Постановка.** Каждую подзадачу передаёт агенту `implementer` (`.claude/agents/implementer.md`, модель Sonnet)
   с самодостаточным ТЗ: цель, файлы, контракт/сигнатуры, критерии готовности, команды проверки, что нельзя трогать.
   Агент стартует без контекста разговора — всё нужное должно быть в ТЗ.
3. **Параллельность.** Независимые подзадачи запускает параллельно; зависимые — последовательно.
4. **Ревью.** Проверяет результат: читает diff, запускает тесты/линтер, сверяет с контрактом. Замечания
   возвращает тому же агенту (SendMessage), а не переписывает сам.
5. **Сам** основной агент делает только: планы, ТЗ, контракты (`docs/contracts/`), правки документации,
   мелкие исправления в 1–2 строки после ревью.

Исключение — пользователь явно попросил сделать что-то самому, без агентов.

## Бэкенд: соглашения

- Стек (предложен, см. план): Python 3.12, FastAPI, SQLAlchemy 2 (async) + Alembic, PostgreSQL, aiogram 3, pytest.
- Контракт первичен: сначала меняем `docs/contracts/openapi.yaml`, потом код. Ответы API обязаны ему соответствовать.
- Всё время хранится в UTC с таймзоной (`timestamptz`); в API — ISO 8601 со смещением + IANA-таймзона точки.
- Логика подбора (`matching`) — чистые функции без БД и без зависимости от формата поставщика рейсов.
- Транспорт абстрагирован: `TransportTrip` + `Location(kind=airport|station)`; авиа-специфика — отдельно.

### Слои и соглашения API

- `app/api/v1/*` — тонкие роутеры: разбор запроса, вызов сервиса, сборка ответа. Без SQL и бизнес-правил.
- `app/services/*` — сценарии (use cases). Функция-сценарий сама делает `await session.commit()` в конце;
  вспомогательные функции только `flush()`.
- `app/schemas/*` — Pydantic-модели строго по `openapi.yaml`. Входные модели — `extra="forbid"`.
  Частичное обновление (PATCH) различает «поле не передано» и `null` через `model_fields_set`.
- Ошибки — только `AppError(ErrorCode.X, "русский текст", status)`.
- Доступ: не член группы и не админ → `404 NOT_FOUND` (не раскрываем существование); член группы, но не
  админ, на админском действии → `403 FORBIDDEN`.
- Тесты API: каждый ответ (и успешный, и ошибка) проверяется на соответствие контракту хелпером
  `tests/helpers/contract.py`. Тесты с БД — через фикстуры `tests/db.py` (Postgres из `docker compose up -d db`, порт 5434).
